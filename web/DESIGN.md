# Web Workbench Design Conventions

## Purpose and boundaries

This is a personal LAN entry point for Codex conversations. Directories and sessions appear on the left, and the conversation appears on the right. Interaction is allowed only after explicitly obtaining the browser-window connection and session ownership. The interface provides no spectator mode and does not invent missing state. It has no authentication and must not be exposed to the public internet.

## Visual system and components

Use the confirmed Open Design workbench as the visual reference: raised near-white navigation, a cool near-white reading canvas, dark text, and cobalt for primary actions, selection, focus, and links. Colors, typography, and spacing come from the root `tokens.css`; the reference's spacing names are adapted to the existing scale rather than copied mechanically. Use `--color-rule` for structural separators, `--color-control-border` for input, button, and dialog boundaries, and dedicated `--color-selected` and `--color-selected-border` tokens for selected items. Do not merge these roles back into one generic gray border. Control borders are deliberately stronger than the reference to retain a calculated 3:1 boundary contrast on light surfaces. Use Inter for headings and body text, with size and weight establishing hierarchy, and JetBrains Mono for code. Fonts are self-hosted by the build, with sans-serif fallbacks and no font CDN. Buttons use the project's shadcn/ui primitives. Keep the prototype and mock data outside the public source tree.

The page uses a Workbench macro layout. The raised navigation rail handles orientation, while the main canvas handles reading and actions. Use stable borders between regions, restrained shadows for overlays and the inset composer, and no decorative gradients. The desktop rail is fixed at 19.5rem. The conversation column is capped at 56.25rem, with wider screens adding canvas whitespace rather than longer message lines. Both top bars share a 3.75rem minimum height; content can grow rather than clip. Session context shows a small directory crumb above the stronger session title. Directory names are at least as large as session names, with greater weight; secondary paths and session metadata use the smaller text token. The timeline is the only expandable main region, and the composer is a stable bottom workbench with a quiet bordered inner surface. Toolbar, timeline, queue and composer share one content axis. Composer height is bounded and scrolls locally when attachments or text would otherwise consume the viewport.

Conversation hierarchy follows stable message semantics rather than title text, session identity, or path. Codex replies use open document-style typography. User messages use a subtle right-aligned surface and do not repeat a "You" heading or copy the prototype's left-hand user avatar. All other non-approval events use a compact bordered inline surface with smaller titles and tabular numbers. Do not introduce mock event statistics or infer extra state from prose. Failures add only an error tone while preserving the original title and reason. Approval and action-only messages retain dedicated interaction structures. Temporary run text uses the shared Bridge message-length truncation and is not truncated again in the Web UI; user and Codex dialogue is never truncated. Show "Sending" while a send is pending. Once Bridge accepts a message, preserve the internal stable state without adding "Received" or "Task not complete" notices. Rejections and unknown results remain visible. After restored history and locally cached messages, show one "Messages above are history" divider instead of repeating a source icon on every message.

Approval messages keep their original title and body as the content layer that explains what is requested and why. The card contains only status, availability, input, and actions; it does not infer another title. Mark open approvals with a top status line and separate the status label from its explanation. Terminal states collapse to read-only results and no longer look actionable. Input approvals show named JSON fields and a stable error area before submit and exit actions. Approve once is primary, approve for session is secondary, reject is dangerous, and cancel is weak. Disabled controls must directly state whether the blocker comes from the connection, permissions, runtime, or request lifecycle.

## State and interaction

Selection color is independent of real connection state. An unknown state never shows a green activity dot. Disconnected state is neutral; expired connections or network loss use a warning tone with explicit text; only operation failures use an error tone. A green dot on a loaded session means only that Bridge has confirmed its current runtime state. Disabled primary buttons use a light surface and muted text rather than an opaque dark fill that still dominates the hierarchy. Losing window ownership preserves static content and drafts but stops subscriptions and actions. Cached data never authorizes approvals, permissions, or runtime state. Sending and approvals do not retry automatically or optimistically announce success. Approvals update in place, and approval does not mean execution succeeded.

Directory navigation may register any existing accessible directory on the Bridge machine without an additional root-path allowlist. Registration stores only a navigation entry and reads existing sessions. It does not create a folder, session, or task, and it does not change the selected conversation. Registering a duplicate locates the existing directory. Empty directories remain visible and are labeled "No sessions."

Directory rows use the basename as the primary identifier and a shortened parent path for disambiguation. Search and hints continue to use the full path. A directory belongs to "Open projects" when Bridge confirms that it contains at least one active, non-archived session. Multiple open projects are allowed and appear first. The selected session controls only its own highlight and never its directory group. Other directories keep their relative order. Directory-level creation appears only while the directory is expanded, hovered, or keyboard-focused; it must remain available after expansion on touch devices.

## Layout and accessibility

Desktop uses two columns from 56rem, leaving room for the navigator and readable conversation; it does not copy the prototype's much wider desktop breakpoint. On narrow screens, directory navigation defaults to a compact entry and expands into a near-full-height panel below the service header, over the conversation. The session list scrolls independently without changing the conversation or composer size. Selecting a session, clicking the backdrop, or pressing Escape closes the panel. The directory toolbar provides "Locate current session": it clears search, returns to the normal view, expands the containing directory, and scrolls the current entry to the middle of the viewport. Disable it for archived views or when no current session exists. Widths of 320, 375, 414, and 768px must not produce horizontal scrolling. The toolbar, timeline, queue, and composer share the 56.25rem content axis; outer whitespace belongs to the canvas and never becomes a third column. Session details use a right-side drawer, becoming a bottom sheet at 40rem and below; both reuse the same modal and real data. Visible labels, keyboard focus, and primary actions are at least 44px; compact information icons are at least 24px. Maintain sufficient contrast. Body text wraps, while code and tables scroll locally. Keep only button-press feedback and disable it when reduced motion is preferred. Static tests and builds do not establish rendered layout, contrast, keyboard or touch acceptance; these still require Playwright MCP review.

All modal dialogs share one keyboard convention. Opening focuses the primary input or first actionable control. Tab and Shift+Tab cycle within the dialog. Escape and backdrop clicks close it only while it is not busy. Closing returns focus to the original trigger.

Keep the sidebar's fixed region compact. Normal service connection status is folded into the brand row; show a full status row only for disconnection, expiration, or required action. User actions are consistently named "Connect to service" and "Take over service connection" so the Web UI itself is not mistaken for the connection target. Before the first connection or directory load, do not render search, the Sessions heading, or unavailable controls. After connecting, show only a compact loading state and provide retry on failure. If stale directories exist during disconnection, retain them for identification. Search uses its placeholder to explain its purpose and keeps an accessible label. When search contains text, Escape clears it and retains focus. Only when search is empty does Escape continue to the directory-panel close behavior. Sessions uses an in-rail heading level. Keep clear spacing between status help and directory actions. Locate, add, and refresh use SVG icons with the same size and stroke width. Directory groups and entries live in one independent scrolling region with no scroll-triggered collapsing.

The sidebar uses explicit, stable directory ordering. Bridge-confirmed open projects appear first. Other directories with content sort by the latest `updatedAt` in the current view. Manually registered directories with no normal sessions sort last by path. Sessions within a directory also sort by `updatedAt`, falling back stably to name and thread ID when time is missing. Only Bridge's session `connection` state affects the Open projects group; ownership, loading, and selection do not change ordering. Normal and archived sessions are separate views. The normal list, search, count, and directory activity time exclude archived sessions entirely. The archived entry sits at the top of the directory scrolling region. The archived view shows only directories with archived sessions and returns to the normal view after a restore. Never sort by unstable or inferred archive timestamps.

Stable explanatory text that does not require immediate action belongs in the shared information hint, shown on hover or keyboard focus. Every icon has a clear accessible name. Text and its hint icon use a consistent 3px visual gap and vertical alignment, without title- or message-specific exceptions. Current network, permission, approval, error, unknown-result, and action-consequence information remains directly visible. Do not hide it in a hint. Each view reduces status help to one current reason and one next step. Empty states do not repeat an existing connection or permission reason. On narrow screens, the composer first shows one line with the current restriction, then places attachment, queue, and send controls in a separate action row rather than relying on wrapping.

Binding has no human approval stage. The interface consistently uses "Bind," "Waiting to bind," and "Cancel wait," never wording that implies an application requiring approval. Binding receipts pass through a centralized presentation mapping; internal reasons such as `unavailable` and `stale` are never interpolated into UI text. Operation results, errors, loading, locate failures, and empty states use `ConversationNoticeArea` and `ConversationNotice` after the top bar. They share one content axis and 8px vertical spacing. Differences are expressed only through explicit status or context and tone semantics; do not maintain two location-specific style systems. The sidebar shows only short status. The composer explains only sending restrictions. Each location states only the currently unmet condition. Empty-state headings are optional and use body-level hierarchy. Unbound states omit a redundant title and retain only the post-bind behavior explanation. A selected session that still awaits connection or catalog confirmation does not repeat a generic unavailable empty state. Native ID copy remains in the session menu and is not duplicated in the top bar. Binding, cancellation, and similar results remain silent when the new UI state already communicates success. Failures and unknown outcomes use the structure "what happened + next step."

The Web composer exposes only the image inputs explicitly supported by App Server. File selection and clipboard paste accept PNG, JPEG, WebP, and GIF, with the server rechecking MIME type and file signature. Do not present arbitrary file-path mentions as a generic attachment capability. Pending images use fixed-size previews. Text drafts and images are isolated by browser tab and session. Refresh and session switching restore them, while separate browser tabs do not overwrite one another. Successful sending or queueing clears them; rejection and unknown results preserve them; expired data is cleaned automatically. Enter sends and Shift+Enter inserts a line break. Input method composition never sends. Within the navigation rail, the search box remains visually quieter than the brand, groups, and selected session until focused. User messages use a compact independent surface aligned to the right; code styling applies only to actual code inside a message. Information popovers and action menus both close on outside click and Escape. The archived entry has a subtle navigation surface by default, with selected styling only in the archived view.

## Prohibited patterns

Do not add a marketing hero, fake statistics, inferred green dots, automatic connection takeover, automatic retries after unknown results, executable approvals from cache, direct rendering of message HTML, or controls for unimplemented features.
